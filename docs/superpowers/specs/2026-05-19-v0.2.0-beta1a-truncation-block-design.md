# v0.2.0-β1a Design — TruncationBlock + Compactor Refactor

**Status:** Draft v2 (post-codex-review, addresses 14 findings)
**Date:** 2026-05-19 (revised 2026-05-20)
**Author:** Brainstorming session 2026-05-19; revisions per codex APPROVE_WITH_REVISIONS
**Targets:** lingyia v0.2.0-β1a (first sub-PR of v0.2.0-β1 release cycle)
**Depends on:** v0.2.0-alpha (shipped, tag `v0.2.0-alpha`)
**Followed by:** β1b (Streaming events), β1c (Session API)

---

## 1. Goal

Decouple the `TokenAwareCompactor` truncation marker from text-encoding. Move from the text sentinel (`Message(SYSTEM, [TextBlock("[lingyia:compactor-marker] earlier N messages truncated")])`) to a first-class `TruncationBlock` member of the `ContentBlock` discriminated union.

The marker text currently serves two purposes simultaneously:
- **Internal protocol:** compactor regex-parses `count` from the text on subsequent compactions
- **Display content:** sent to the LLM provider as SYSTEM text so the model knows context was truncated

This dual purpose was flagged in `CHANGELOG.md` as a deferred refactor at v0.2.0-alpha tagging time. β1b adds token-level streaming; without this refactor, `text_delta` events would emit the marker prefix one character at a time (`"["`, `"l"`, `"i"`, `"n"`, ...), leaking internal protocol to end users.

## 2. Non-Goals

- Plugin block registry (custom user-defined `ContentBlock` subtypes). Deferred to v0.3.
- Streaming event integration. β1b will reference the forward contract defined in §10.
- Session-API checkpointer auto-load/save wiring. β1c.
- Removal of legacy text-marker detection. Stays through one transitional version; targeted for v0.4 removal.

## 3. Design Decisions (locked from brainstorm)

1. Marker stays in `RunState.messages` (not metadata-only). Reason: `messages` is the source of truth in v0.2-α; metadata-only would require every adapter/exporter to synthesize a phantom message.
2. Marker uses `Role.SYSTEM`. No new `TRUNCATION_MARKER` role. Roles map to provider conversation roles; adding a non-provider role spreads special cases everywhere.
3. `TruncationBlock` joins `ContentBlock` union with `type: Literal["truncation"]` discriminator.
4. `ContentBlock` semantics widen: from "model-native content" to "transcript-projectable content" (now includes runtime-authored blocks).
5. `BlockKind` enum does NOT add `TRUNCATION`. Capability checks skip `TruncationBlock`. Rationale: `BlockKind` is the model capability vocabulary; `TruncationBlock` is runtime-authored, never seen by the model directly.
6. Runtime validates that `TruncationBlock` originates only from runtime authorship: model outputs and tool results carrying `TruncationBlock` raise `CapabilityViolationError`.
7. Adapter wire-encoding flattens `TruncationBlock` to text at the provider boundary (`f"[earlier {count} messages omitted]"`).
8. Legacy v0.2.0-alpha text-encoded markers remain readable for one transitional version with a `DeprecationWarning`; next `compact()` call rewrites to `TruncationBlock`.

## 4. Block-Level Changes

### 4.1 New `TruncationBlock` dataclass

`lingyia_core/blocks.py`:

```python
@dataclass(frozen=True)
class TruncationBlock:
    """Runtime-authored marker indicating prior messages were dropped during compaction.

    Compactor-authored only. Flattened to text by adapters before sending to
    LLM providers. Not a model capability — does NOT appear in BlockKind enum
    or ModelCapabilities.{accepts,emits}.

    Attributes:
        count: Cumulative count of messages dropped across all compactions
               since the start of this conversation. Monotonically non-decreasing.
               MUST be a positive integer (`count > 0`); a TruncationBlock
               with count=0 has no meaning — if no messages have been dropped,
               no marker should exist.
    """
    count: int
    type: Literal["truncation"] = "truncation"

    def __post_init__(self) -> None:
        if not isinstance(self.count, int) or self.count <= 0:
            raise ValueError(
                f"TruncationBlock.count must be a positive integer, got {self.count!r}"
            )
```

**Construction-time enforcement (per codex P2.6).** Compactor estimation passes
that previously called `_make_truncation_marker(prior_count + 0)` must be
rewritten to either (a) reuse the existing marker message instead of
constructing a placeholder with count=0, or (b) skip estimation when no
drops are pending. Estimation never constructs a real `TruncationBlock`
with count=0.

## 5. Capability Check Adjustment

`lingyia_core/capability.py` `_collect_block_kinds`.

**Key constraint (per codex P1.3):** the existing implementation recurses
into `ToolResultBlock.content` (which may itself be a `tuple[ContentBlock, ...]`
per `blocks.py:103`). The spec MUST preserve that recursion; a flat
top-level walk would silently bypass capability checks for nested image,
audio, or thinking blocks. The new behavior is identical except that
`TruncationBlock` is skipped at every recursion depth.

```python
def _collect_block_kinds(messages: Iterable[Message]) -> frozenset[BlockKind]:
    kinds: set[BlockKind] = set()

    def visit(block: ContentBlock) -> None:
        if isinstance(block, TruncationBlock):
            return  # runtime-only, not a model capability — skip at every depth
        kinds.add(BlockKind(block.type))
        # Recurse into nested ContentBlock sequences (currently only
        # ToolResultBlock.content can be a tuple of ContentBlocks).
        if isinstance(block, ToolResultBlock) and isinstance(block.content, tuple):
            for nested in block.content:
                visit(nested)

    for m in messages:
        for b in m.content:
            visit(b)
    return frozenset(kinds)
```

This is the only place capability checking touches block kinds. Skipping `TruncationBlock` means:
- `accepts` check never rejects state that contains a `TruncationBlock` (at any depth)
- `emits` check never inspects a `TruncationBlock` (covered by §6 instead)
- Nested image/audio/thinking blocks inside `ToolResultBlock.content` continue to participate in `accepts` checks as before

## 6. Runtime Authorship Validation

`lingyia_core/runtime.py` adds three validation paths backed by one shared helper.

### 6.0 Shared helper — `_find_runtime_block`

Per codex P2.7, runtime-authored block detection must traverse nested
`ToolResultBlock.content` (which can itself be `tuple[ContentBlock, ...]`).
A single recursive helper is used by every callsite so the recursion is
uniform:

```python
def _find_runtime_block(
    content: Iterable[ContentBlock] | str,
) -> Optional[ContentBlock]:
    """Return the first runtime-authored ContentBlock found at any depth,
    or None if the content contains no runtime-authored blocks.

    Currently the only runtime-authored block is TruncationBlock.
    Returns the offending instance so callers can include it in error
    messages. Returns None for plain `str` content.
    """
    if isinstance(content, str):
        return None
    for b in content:
        if isinstance(b, TruncationBlock):
            return b
        # Recurse into nested ContentBlock sequences.
        if isinstance(b, ToolResultBlock) and isinstance(b.content, tuple):
            nested = _find_runtime_block(b.content)
            if nested is not None:
                return nested
    return None
```

Used by §6.1 (model output), §6.2 (tool result), §6.3 (approval resume),
and indirectly by §5 (capability traversal, which uses its own recursion
but the same skip rule).

### 6.1 Model output validation — runs BEFORE `_enforce_emits`

After `adecide` returns a `Decision`, but **before** the existing
`_enforce_emits(decision, capabilities)` call (per codex P1.1).

Ordering rationale: `_enforce_emits` calls `BlockKind(block.type)` on every
block in `decision.content`. Since `TRUNCATION` is intentionally absent
from `BlockKind` (per §3 decision 5), `BlockKind("truncation")` would
raise `ValueError` before this runtime-block check could run. The
TruncationBlock detection MUST execute first so model violations are
reported with a clear `CapabilityViolationError`, not an opaque
`ValueError` from inside `_enforce_emits`.

```python
def _validate_no_runtime_blocks_from_model(self, decision: Decision) -> None:
    """Reject TruncationBlock in model output (runtime-authored only)."""
    offending = _find_runtime_block(decision.content)
    if offending is not None:
        raise CapabilityViolationError(
            f"Model {self.model.capabilities.model_id!r} emitted a "
            f"{type(offending).__name__}; runtime-authored block kinds "
            "cannot originate from model output."
        )
```

Call ordering in the runtime loop:

```python
decision = await self.model.adecide(...)
self._validate_no_runtime_blocks_from_model(decision)  # NEW — runs first
self._enforce_emits(decision, capabilities)            # existing, unchanged
# ... append decision to state.messages ...
```

### 6.2 Tool result validation — uses `result.output` and recurses

After a tool returns a `ToolResult` and the runtime calls
`_serialize_tool_output(result.output)` (`runtime.py:644`), validate the
serialized output via the shared helper from §6.0.

Two corrections from spec v1 (per codex P1.2 and P2.7):
- The dataclass field is `ToolResult.output` (`Any`), NOT `result.content`.
- The validation MUST run on the **serialized** output (which may be a
  `tuple[ContentBlock, ...]` after `_serialize_tool_output`), and MUST
  recurse through any nested `ToolResultBlock.content`.

```python
def _validate_tool_result(
    self, serialized: Union[str, tuple[ContentBlock, ...]], tool_name: str
) -> None:
    """Reject TruncationBlock anywhere in serialized tool output."""
    if isinstance(serialized, str):
        return
    offending = _find_runtime_block(serialized)
    if offending is not None:
        raise CapabilityViolationError(
            f"Tool {tool_name!r} returned a {type(offending).__name__}; "
            "runtime-authored block kinds cannot originate from tool output."
        )
```

Call site (`runtime.py` near line 644):

```python
content = self._serialize_tool_output(result.output)
self._validate_tool_result(content, result.tool_name)  # NEW
result_blocks.append(ToolResultBlock(...content=content...))
```

### 6.3 Approval-resume validation — runs in `aresume`

Per codex P2.8, the `aresume()` path at `runtime.py:368` appends
`interrupt.pending_decision.content` directly. Pending decisions can be
restored from checkpoints (`state.py:280`), so a malicious or corrupted
checkpoint could inject a TruncationBlock via pending decision and bypass
§6.1.

`aresume` MUST re-validate pending decisions through the same shared
helper before appending or executing them:

```python
async def aresume(self, harness, state, approved, feedback):
    interrupt = state.interrupt
    # ... existing guards ...
    if interrupt.pending_decision is None:
        raise RuntimeError(...)

    # NEW (per codex P2.8): re-validate pending decision content
    # before appending or executing.
    offending = _find_runtime_block(interrupt.pending_decision.content)
    if offending is not None:
        raise CapabilityViolationError(
            f"Pending decision restored from interrupt/checkpoint contains "
            f"{type(offending).__name__}; runtime-authored block kinds cannot "
            "be carried through an approval resume."
        )

    # ... existing append + execute ...
```

This closes the checkpoint-injection vector. The same helper is used so
behavior is identical to model-output validation.

## 7. Compactor Changes

`lingyia_kit/compactors/token_aware.py`.

### 7.1 Emission

```python
@staticmethod
def _make_truncation_marker(count: int) -> Message:
    return Message(
        role=Role.SYSTEM,
        content=(TruncationBlock(count=count),),
    )
```

### 7.2 Detection (with legacy compat)

Per codex P2.5, the marker predicate is tightened: a new-format marker
requires `role == Role.SYSTEM` AND a single-element content tuple holding
exactly one `TruncationBlock`. This prevents a malformed USER/ASSISTANT
message that happens to contain a `TruncationBlock` from being swallowed
by the compactor and re-emitted as SYSTEM — runtime authorship validation
(§6) already rejects such messages from model/tool sources, but the
defense-in-depth narrows the predicate so even a hand-crafted state
cannot smuggle non-SYSTEM markers through compaction.

```python
@staticmethod
def is_truncation_marker(msg: Message) -> bool:
    # New format: SYSTEM role + single-block TruncationBlock content
    if (
        msg.role == Role.SYSTEM
        and len(msg.content) == 1
        and isinstance(msg.content[0], TruncationBlock)
    ):
        return True
    # Legacy text marker (transitional, v0.4 removal)
    if msg.role == Role.SYSTEM:
        for b in msg.content:
            if isinstance(b, TextBlock) and b.text.startswith("[lingyia:compactor-marker]"):
                return True
    return False
```

A non-SYSTEM message containing a `TruncationBlock` is treated as
ordinary transcript content by the compactor (not a marker) and is
flattened to text by adapters with a warning (see §9 edge case 1).

### 7.3 Count parsing (with legacy compat)

```python
_LEGACY_MARKER_COUNT_RE = re.compile(r"earlier (\d+) messages")

@staticmethod
def _parse_marker_count(msg: Message) -> int:
    # New format
    for b in msg.content:
        if isinstance(b, TruncationBlock):
            return b.count
    # Legacy text fallback
    for b in msg.content:
        if isinstance(b, TextBlock):
            m = _LEGACY_MARKER_COUNT_RE.search(b.text)
            if m:
                warnings.warn(
                    "Loaded a v0.2.0-alpha text-encoded truncation marker. "
                    "Next compact() will rewrite to TruncationBlock. "
                    "Legacy text marker support will be removed in v0.4.",
                    DeprecationWarning,
                    stacklevel=2,
                )
                return int(m.group(1))
    return 0
```

### 7.4 Removed/deprecated constants

Mark `_MARKER_PREFIX = "[lingyia:compactor-marker]"` as deprecated (kept for legacy detection only). Document removal target as v0.4.

## 8. Adapter Wire-Encoding

`lingyia_kit/adapters/_openai_base.py` and `lingyia_kit/adapters/anthropic.py`
each add a **per-role projection helper** that walks `msg.content` in
declaration order and inlines every `TruncationBlock` as text before the
adapter's existing block-handling paths run.

Per codex P1.4 and P2.9: spec v1 only handled "TruncationBlock-only"
messages. A `Message(SYSTEM, [TextBlock, TruncationBlock])` would have
been silently dropped (OpenAI adapter logged a warning then fell through;
Anthropic system extraction ignored non-text blocks entirely). The
projection must produce wire text for every TruncationBlock regardless
of whether the message also carries other content.

### 8.0 Shared flattening helper

Both adapters share the text formatter:

```python
def _truncation_to_text(b: TruncationBlock) -> str:
    return f"[earlier {b.count} messages omitted]"
```

### 8.1 OpenAI-compatible base — per-message projection

```python
def _project_message_to_wire(self, msg: Message) -> list[dict]:
    """Project one transcript Message into one-or-more OpenAI wire messages,
    inlining TruncationBlock as text in declaration order before existing
    block handling runs.

    Returns a list because, in degenerate mixed cases, a single transcript
    Message could produce a leading system text + a primary role message.
    For the common case (TruncationBlock-only SYSTEM marker, or no
    TruncationBlock at all), returns a single-element list.
    """
    # Fast path: no TruncationBlock — delegate to existing per-block handling
    if not any(isinstance(b, TruncationBlock) for b in msg.content):
        return self._build_wire_message_existing(msg)  # current logic

    # Walk content in order, splitting around TruncationBlock instances.
    # Each TruncationBlock contributes a system-role wire message with
    # its flattened text. Non-TruncationBlock runs are passed to the
    # existing per-block handler under the original role.
    out: list[dict] = []
    buffer: list[ContentBlock] = []

    def flush_buffer_under(role: Role) -> None:
        if not buffer:
            return
        out.extend(self._build_wire_message_existing(
            Message(role=role, content=tuple(buffer))
        ))
        buffer.clear()

    for b in msg.content:
        if isinstance(b, TruncationBlock):
            flush_buffer_under(msg.role)
            out.append({"role": "system", "content": _truncation_to_text(b)})
        else:
            buffer.append(b)
    flush_buffer_under(msg.role)
    return out

def _build_messages(self, context: dict, state: RunState) -> list[dict]:
    out = []
    for msg in state.messages:
        out.extend(self._project_message_to_wire(msg))
    return out
```

This guarantees:
- TruncationBlock-only SYSTEM markers produce one system message with `_truncation_to_text(b)`.
- Mixed `Message(SYSTEM, [TextBlock, TruncationBlock])` produces a system message with the TextBlock text followed by a system message with the truncation text — block order preserved on the wire.
- Non-SYSTEM TruncationBlock (defensive case; should never happen post-§6) still flattens to text under role=system with a warning at projection time.

### 8.2 Anthropic adapter — single ordered system-projection helper

Anthropic's system content goes into a top-level `system` payload, not an
inline message. Per codex P2.9, the spec defines a single ordered helper
that walks each SYSTEM message in order, producing text per block:
`TextBlock → as-is`; `TruncationBlock → _truncation_to_text(b)`. Each
SYSTEM message's per-block text is concatenated in block declaration
order; multiple SYSTEM messages are joined per the existing
newline-joining convention at `anthropic.py:221`.

```python
def _project_system_message(self, msg: Message) -> str:
    """Project one SYSTEM Message into a single system payload string,
    walking content in order. TruncationBlock and TextBlock both contribute
    text; other block types are skipped with a warning (Anthropic system
    payload only accepts text)."""
    parts: list[str] = []
    for b in msg.content:
        if isinstance(b, TextBlock):
            parts.append(b.text)
        elif isinstance(b, TruncationBlock):
            parts.append(_truncation_to_text(b))
        else:
            logger.warning(
                "Anthropic system payload received non-text/non-truncation "
                "block %r; ignoring.", type(b).__name__,
            )
    return "".join(parts)  # block-order concatenation; no separator

# Caller-side in _build_messages:
system_parts: list[str] = []
for msg in state.messages:
    if msg.role == Role.SYSTEM:
        system_parts.append(self._project_system_message(msg))
        continue
    # Non-SYSTEM messages: walk msg.content; if any TruncationBlock appears
    # (defensive), inline as text in user/assistant content per existing
    # text-handling path. Use the same per-block projection pattern as §8.1.
    out.extend(self._project_non_system_message(msg))

# Existing concatenation convention preserved:
system_payload = "\n".join(p for p in system_parts if p)
```

This guarantees that `Message(SYSTEM, [TextBlock("You are…"), TruncationBlock(count=12)])`
produces a system payload containing both the original system prompt and
the flattened truncation marker, in declaration order. The marker text
reliably appears on the wire even in mixed-content system messages.

## 10. Forward Contract for β1b Streaming

β1b will add `StreamEvent` discriminated union. The following contract is
locked **here, now, and verbatim** (per codex P2.10) — β1b spec MUST
reference this section by anchor, not paraphrase. The "optional"
language from spec v1 is replaced with hard ordering and emit-condition
rules.

### 10.1 Event vocabulary

```
text_delta(text: str)        ← derived ONLY from TextBlock token stream
thinking_delta(text: str)    ← derived ONLY from ThinkingBlock token stream
truncation(payload)          ← structured event, emit-conditional (see §10.2)
tool_use(block: ToolUseBlock)     ← complete block, one event
tool_result(block: ToolResultBlock) ← complete block, one event
... (other StreamEvent kinds defined in β1b spec)
```

### 10.2 `truncation` event emit rules — LOCKED

The compactor already emits a `TelemetryEvent(kind="compacted")` at
`runtime.py:400` whenever it runs. The streaming `truncation` event is
distinct from this telemetry event and has the following contract:

1. **Emit condition.** When the compactor runs mid-stream AND produces a
   new `TruncationBlock` (`cumulative_count` strictly increases over the
   prior state), the stream MUST emit exactly ONE `truncation` event.
2. **No emit on no-op.** If the compactor runs but produces no new
   `TruncationBlock` (e.g., state already under budget, or irreducible
   floor reached with no new drops), NO `truncation` event is emitted.
3. **Ordering.** The `truncation` event MUST emit **immediately after**
   the existing `TelemetryEvent(kind="compacted")` and **before** the
   next iteration's events (model deltas, tool events, etc.).
4. **Payload.**

   ```python
   {
       "newly_dropped": int,      # messages dropped in THIS compaction
       "cumulative_count": int,   # TruncationBlock.count after this compaction
   }
   ```

   Both counts are present for clarity; clients can derive whichever they
   need. `cumulative_count` matches the `TruncationBlock.count` field
   that ends up in state.messages.
5. **Never `text_delta` from flattened text.** `TruncationBlock`
   instances in `state.messages` NEVER produce `text_delta` events. The
   adapter-flattened text (`"[earlier N messages omitted]"`) is a
   provider-boundary concern; the streamer sees `TruncationBlock`
   directly and emits the structured event per (1)–(4).

### 10.3 β1b dependency

This section is a **hard β1b dependency.** The β1b spec MUST link to
§10.2 by anchor and inherit these emit rules verbatim. Any deviation
(adding optional emit modes, payload extensions, ordering changes)
requires amending this section first, not β1b alone.

## 11. Backward Compatibility Story

### 11.1 v0.2.0-alpha snapshots

ai-agent backend (`app/backend/`) currently uses lingyia v0.2.0-alpha and may have text-encoded markers in its `SqliteCheckpointer` DB.

Compactor reads BOTH formats in β1a (§7.2, §7.3). On next `compact()` invocation:
- Legacy text marker `count` is parsed via regex
- Compactor adds newly-dropped count to legacy count
- A new `TruncationBlock` replaces the legacy text marker
- Subsequent compactions only see the new format

This requires zero data migration step. Database snapshot continues to load; first compact write rewrites in place.

**Concurrency caveat (per codex P2.11).** `SqliteCheckpointer` at
`sqlite.py:61` uses last-writer-wins upsert. If two runtimes compact the
same `session_id` simultaneously, both may compute counts from the same
prior state and the later writer overwrites the earlier one — losing
one update. **Concurrent compactions on the same `session_id` are
best-effort under v0.2.0-β1a.** Optimistic versioning / CAS will be
introduced in v0.2.0-β1c alongside the session-API checkpointer
contract. In practice the ai-agent backend serializes compaction per
session, so this race is not currently exposed in production.

| Version | Status |
|---|---|
| v0.2.0-β1a (this release) | Both formats readable; new compactions emit `TruncationBlock`; `DeprecationWarning` on legacy read |
| v0.2.0 stable, v0.3.x | Same |
| v0.4.x (estimated) | **Hard removal.** Legacy text-marker detection removed entirely from `is_truncation_marker`, `_parse_marker_count`, and `_LEGACY_MARKER_COUNT_RE`. |

**v0.4 hard-removal semantics (per codex P3.14).** In v0.4.x there is no
legacy parse path. A v0.2.0-alpha snapshot that contains only a legacy
text marker will treat the marker text as ordinary `SYSTEM` text — it
will be passed to providers as plain text (no special parsing), and new
compactions will accumulate `TruncationBlock.count` fresh from 0 (since
no new-format marker exists in the snapshot). No crash, no
`DeprecationWarning`, no special case. The legacy text remains in the
transcript as a benign system note until naturally dropped by a future
compaction. Spec v1's "logs error but does not crash; count parsed as 0"
language is withdrawn — it conflicted with "detection removed entirely."

### 11.3 Public API stability

No public API breakage. The `TokenAwareCompactor` constructor signature, `should_compact`, `compact`, `is_truncation_marker` static method all stable. `TruncationBlock` is a new addition to `ContentBlock` union — additive, not breaking.

## 15. Sub-Agent Contract

Per codex P3.13. The current `sub_agent_tool` at `sub_agent.py:120`
returns only `summary`, `status`, `cost`, and `run_id` — none of which
are `ContentBlock` instances. Child `TruncationBlock` markers therefore
cannot leak into the parent transcript today. The spec makes this
**explicit** so future sub-agent variants do not silently re-open this
vector:

> Sub-agent tools MUST NOT expose child `RunState.messages` as rich
> `ContentBlock` instances to the parent runtime. Sub-agent results are
> serialized as text or data summaries in the tool-use return value,
> never as transcript content. A future sub-agent option that exposed
> the child's full message list would have to flatten any
> `TruncationBlock` to text (or omit it) before returning, and would
> still be subject to §6.2 tool-result validation if it returned
> structured `ContentBlock` instances.

This contract lives in the spec because it is a cross-cutting concern
between the sub-agent tool and the runtime authorship validation in §6
— a regression here would silently bypass §6 without raising any error.
